# Agent Guide

## Project Shape

- This is a build-free static PWA: the repository runs as is, including under a subpath. The deploy runs one optional step, `npm run build:site` ([scripts/build-site.js](scripts/build-site.js)), which writes `dist/` with the scripts minified (top-level names kept) and without `data/catalog.json`; CI smoke-tests that output too. See [README.md](README.md) for the full rationale and checks.
- [index.html](index.html) owns the shipped markup and classic inline application JavaScript.
- [assets/app.css](assets/app.css) owns layout, base styles, and theme overrides.
- [assets/accessibility.css](assets/accessibility.css) owns focus, skip-link, reduced-motion, and mobile performance styles.
- [assets/accessibility.js](assets/accessibility.js) owns keyboard and ARIA behavior for dynamic strategy rows.
- [data/catalog.json](data/catalog.json) is the catalogue's source of truth, published to the database when it merges to `main` (the Publish catalogue workflow, `publish_catalog_with_key`) or from the admin page (`publish_catalog`); the app reads it through `get_catalog()` and the file is never deployed. [data/catalog.js](data/catalog.js) only restores the browser's saved copy into `CATALOG_DATA` before the first refresh. Referral links never reach the browser: `launchUrlFor()` sends OPEN through the `go` edge function for platforms flagged `hasReferral`. A Pro account's own link (the edit sheet's referral field, mirrored to `member_links`) comes first; a platform imported from a friend's shared list carries its `shareCode` and adds `&via=<launch token>` so the database can serve the sharer's link when both hold Pro (see README, *Pro referrals and shared lists*).
- [sw.js](sw.js) owns offline caching and same-origin network behavior.

## Working Rules

- Preserve classic scripts, global functions, inline `onclick` handlers, and the current script-loading order unless deliberately migrating the whole architecture.
- Use two-space indentation, semicolons, and existing naming patterns.
- Keep local URLs relative; the app may run under a GitHub Pages subpath.
- Treat localStorage keys and persisted state as public contracts. Add migration logic before changing a key.
- Do not add frameworks, bundlers, or unrelated refactors. The one runtime exception already in place is `supabase-js`, loaded via CDN `<script src>` (see Cloud Sync below) the same way Google Fonts already is - no bundler, nothing to `npm install` to run the app. The only dev dependency is `terser`, used by the deploy step alone. The second, agreed for the landing intro: three.js, vendored (minified, unmodified) in `assets/vendor/three/` and loaded only by the WebGL intro (`assets/intro3d/intro.mjs`) and the table it flies into (`assets/intro3d/table.mjs`, which also uses the addons' `CSS3DRenderer` for the page elements laid on the table) through a dynamic `import()` - and, the same way, by Obsidian Ledger's orrery (`assets/intro3d/orrery.mjs`, its Lounge payout, fetched the first time it plays) and Neon Grid's moonrise (`assets/intro3d/moonrise.mjs`, likewise) - see `assets/vendor/three/README.md` for the version and how to update it. Don't add further dependencies beyond that without deliberate discussion.
- Catalog edits must preserve required fields and optional metadata; tracked user copies are persisted separately from the catalog.
- Dynamic interactive rows must retain the existing accessibility behavior.

## Validation

Run from the repository root:

```bash
npm run check
npm run check:syntax
npm run check:refs
npm run check:catalog
npm run test:smoke                 # browser flows against a fake Supabase
npm ci && npm run build:site && SMOKE_ROOT=dist npm run test:smoke
```

The authoritative script definitions are in [package.json](package.json), and CI runs the full check through [.github/workflows/checks.yml](.github/workflows/checks.yml). Use the narrowest relevant check first, then the full suite for cross-file changes.

## Theme Work

- Theme definitions live in the inline `THEMES` object in [index.html](index.html). Object order is picker order.
- Theme variables, `bodyBg`, and browser `theme-color` are applied through the existing theme engine and exposed via `data-theme`.
- Skins come in pairs: a **visualized** skin and its **muted** pairing - same colours, different effects. A visualized skin names its pairing in `look` (it wears that theme's palette and every `[data-theme="<look>"]` rule) and the table the landing flies into in `table` (its home; see `assets/intro3d/table.mjs`). `applyTheme()` sets `data-theme` to the look and `data-skin` to the skin itself, so rules that are the visualized skin's own effects (for Refinement × Realization: the drifting three-tone mesh, the sweep on the gold) are scoped `[data-skin="<id>"]`, while the room both share - for Executive Lounge: black cards on brushed obsidian, one slow swaying light, a little gold dust - is `[data-theme="<look>"]`. The muted pairing is the quiet, readable take of the same room. Refinement × Realization (`refinement`, the default) / `executive` (once called Executive Lounge; the stylesheet's `[data-theme="executive"]` rules and this guide still name its room so) is the first pair. To the person using it a pair is one skin: the Theme picker (`renderThemeUI()`) lists the visualized skin only, lit while either half is on, with its levels under it; tapping it while on either half goes to the levels (`pickSkin()`), and from another skin it goes to the visualized one. The levels are chosen in Settings' block above the picker, which carries the skin's name (see How much show below); ids and stored `almanac_theme_v1` values are unchanged. Everyone was moved onto it once when it became the default (the `almanac_skin_rxr_v1` flag, set by the pre-paint bootstrap); a skin picked after that is kept. The bootstrap at the top of `index.html` mirrors the look table and must be kept in step.
- The card table (`?dest=card`) is the only destination; `?dest=none` keeps the classic landing. The intro's sound is on unless the speaker switched it off (`almanac_intro_sound`, reset to on once by `almanac_intro_sound_on_v1`); browsers hold a page silent until its first tap or key, so that tap starts it (`createIntro()` in `assets/intro3d/intro.mjs`).
- With motion off (`html[data-motion="off"]`), a visualized skin's pages must be exactly its muted pairing's, and its table is entered with `reduced: true` (a cut to the seat, the cards already dealt, the dealer up at rest, nothing moving after - no gestures).
- The table's dealer (`makeDeal()` in `assets/intro3d/table.mjs`) picks one of six deals each visit (`DEAL_STYLES`) - `single`, `rows`, `columns`, `spread`, `flop` (a row at a time as a hold'em dealer turns the flop: three cards laid in a stack, slid out along the row in one stroke, turned over together) and `pitch` (the shoe's hand alone flicks each card low along its row to land short and slide into place, then knocks twice on the felt and the backs turn over in a wave out from the knock) - and `?deal=<style>` fixes one for testing (`?cards=N` pads the hand to N cards, for the lab; `rollTable.timing` lists each card's pull, toss, pitch, lay and turn times). Every card is laid face down before it turns, so its back is seen; the backs are engraved SVG drawn by `backArt()` per tier and handed to the page as `--r3t-art-<tier>` / `--r3t-foil-<tier>` custom properties. A tapped card comes up in front of the camera and can be dragged to turn it (`focal`, `spinBy()`); the lab's `rollTable.turnCard(dx, dy)` does the same.
- The dealer is a two-armed torso (`buildDealerTorso()`, and `buildDealerArm()` and `buildDealerHand()` for each of `SIDES`) on a telescoping lift under the port. The shoe side's arm draws each card and flicks it across to the other hand, in front of the machine's body, never over it (`TOSS`, `flightAt()`: one flat turn, a little rise, a bow out toward you), and the other hand, open where it will arrive, catches it and gives with it (a `stiff` move: no settle, starting at the card's speed), then lays it and turns it - the pitch releases low, from the height its flight needs (`pitchOf()`), and the card skids to a square stop; after the deal both stay up, at rest (`REST`: one hand on the shoe's lid, the other poised on its fingertips on the felt). Each arm is seven-axis, solved every frame from the shoulder to the wrist, the elbow on the circle round that line where `elbowWay()` steers it (`ELBOW`: out and up at work, back and easy at rest). Its links (`ARM.upper` + `ARM.fore`) must stay longer than the farthest shoulder-to-wrist reach of any deal, or `pose()` clamps the elbow's solve while the forearm is still drawn from the elbow to the wrist, so it stretches past `ARM.fore` - re-measure with the lab's `rollTable.reach()` (every style, 9 cards; the upright it rises in is at full length by design) after moving the port, the layout, the pass, the rest poses or the grab/lay poses. Each arm's plan is a list of segments (`addMove()`: quintic paths, dead still at a stop, joined smooth through via points - still, along any axis the path turns back on - and a servo's settle where it places something). A move that turns the hand a long way round is swung from the wrist (`wrist: true`); about the fingertips it would swing the wrist out past its reach or down through the felt. Re-measure the gestures too (`rollTable.gesture(name, [card])` then `reach()`), and keep the wrist clear of the felt. The hand's wrist attitude (`lean`/`dip`, pivoting at the fingertips, level at every grab, pass and lay) and its fingers (`FIN` presets, played per finger with a lag through `hand.userData.fingers()`) are part of the plan; a grip arches the fingers so the pads rest on the card instead of curling through it. It rises through an iris port (`buildPort()`, a real hole through the felt and the table, which the dealer's own canvas mirrors in depth only - and the iris's closed part too, while it sulks).
- The dealer's canvas (`handGL`, over the cards, under the phone) has its own light and casts real shadows onto the felt, the cards and the shoe's lid (shadow-only catchers); only its body casts - nothing thinner than a few millimetres, no glass, lights or gold - and nothing at all once the intro's quality has stepped down to no shadows. It has its own copy of the intro's studio environment (`studioEnvironment()`, exported from `intro.mjs`, rebuilt in `handGL`'s context, made again on a lost context and dimmed with the house lights), so its glaze, gold inlay and crystals mirror the same room as the table's brass. Each joint's drum ends in a watch caseback: sapphire over a movement (`movementTex()`), a gold bezel and blued screws. The cards are page elements, so each has a depth-only mask in that canvas (the card's rounded shape a fifth of a millimetre behind it along the line of sight, marked in the stencil): whatever of the machine is behind a card is hidden by it, wherever the card is - held out, in the air, or brought up to you (`r3t-focus` dims the room behind it). Each card also casts two shadows along the key light (`shadeCard()`): a tight contact line while it lies on the felt and a wide soft one that fades as it rises, deeper on a light felt, never on the card itself (the stencil). A card lands with a stamp (pressed to 95% for a moment, from `stampAt`), takes one pass of light down it when it comes to rest face up (`.r3t-sync`), and once dealt lifts a centimetre to meet a finger or the pointer with its gilt edge lit (`hover`, `.r3t-hover`); motion off keeps all three still. While the machine sulks the house lights go down with it (`house`/`houseAt()`, `lightHouse()`: the room's mirror, lamp and pendant all but out, the cards still lit, the machine only its edges and its glowing circuits on a peek) and a touch brings them straight back up; motion off keeps them up. Once the deal is done it prompts while a ready card sits uncollected, more plainly the longer it waits (`idleTick()`: a point, a wave, spirit fingers, drumming, then a sulk down the port with a peek now and then); a collect gets a knock of thanks, and any touch or key at the table gives way (`giveWay()`). Nothing ready, it waits quietly. A gesture is more segments on each arm's plan; one that moves only the arms draws only their canvas (`armsLoop()`, at a moving frame's resolution through `world.layer(handGL, true)`, sharp again when it stops), so the table under it stays still and sharp. The lab's `rollTable.gesture(name)` plays one and `rollTable.waiting` reports the wait. The props (chip float, shoe, discard rack) are modelled in `table.mjs`, each held to a real maker in the comment above it (the float: a Macau salon's, piano lacquer with buffed brass caps and screws, its values cut into the strip; the discard's medallion and the port's ring are engraved with `engravedMat()`, not printed). The surface finishes (brushed brass, lacquer peel, blasted steel, clay, open-pore walnut, pebble-grain leather) and the canvas helpers live in `assets/intro3d/finish.mjs`, shared by the shot and the table (`finish(kind)`, `finished(mat, kind, repeatU, repeatV, depth)`). The shot's cup is pebble-grain calfskin burnished at its rim and base with an embossed enamel badge; the stick a porous walnut shaft, a turned brass ferrule and a bent rattan hook - each held to its maker in the comment above it. The table's walnut (`walnutOf()`) is open-pore under a satin lacquer: the pores are a fine tiling normal map (`finish('pores')`, 2 cm a tile) under the clear coat's own faint peel, so the grain stays sharp pinched in - give any new walnut part its UVs in cm along the grain (u) and use `walnutOf()`; the lab's `rollTable.look(eye, aim, fov)` puts the camera anywhere in the seat's frame to look one over (`look()` puts it back).
- The WebGL canvas has two resolutions (`size()` in `assets/intro3d/intro.mjs`). Moving frames use `pixelRatio`: the screen's, to 2x. The intro's quality steps lower it on a slow device, and the table's loop moves it back up or down with the frame rate (`world.pace()`). A frame that stays up is drawn again at the screen's own resolution, to 3x, within a pixel budget: the intro at rest and the table between moves (`world.rest(draw)`, undone by `world.move()`). While the page is pinched in, the canvas at rest covers only the visual viewport and draws that part of the lens (`setViewOffset`) at the zoom's resolution. While the view moves (a pinch or pan at rest, or any moving frame) the crop follows it a frame at a time (`follow()`, `serves()`): the crop already drawn is kept while all of the view is inside it at a zoom within a sixth of its own, and a new one takes a margin round the view (`MARGIN`), so a small pan shows pixels already drawn - never the whole view at a moving frame's resolution, which is blocky pinched in; a moving frame's pixels are spread over the crop, so pinched in it is as sharp as the zoom allows at no more cost. `world.pace()` brings the resolution back after a slow patch, after a wait that doubles each time it has to come down. A new way of drawing the scene must go through `world.paint()`, or it misses the resize and the crop. Another canvas drawn over it with the same camera (the dealer's) registers with `world.layer(gl)`, so it keeps the same size, crop and resolution, and draws through `world.lens(fn)`; placing a canvas clears it, so draw it straight after. The canvas is measured by its own box (the stage), not `world.host`, which is hidden after the arrival.
- Frames are paced to about 60 a second on any screen (`makePacer()` in `intro.mjs`: it learns the display's refresh from the gaps between animation frames and draws every nth), so a 120 Hz phone neither runs the shot faster nor spends twice the work; the table's loop and the arms' loop use their own (`world.pacer()`). Nothing may compile or upload during the shot: `warm()` compiles every material for the renderer's actual targets (the scene as a whole - a subtree compiled alone counts the scene's lights wrong - including what is hidden until later, such as the table's seat) and uploads every texture before the first frame, and the start renders the shot's key moments (the release, the wall strike, the slow hold, the float) on a hidden canvas; the table is warmed the same way before its seat is shown (`prepareTable()` passes `warm`). A lost WebGL context (a phone short of GPU memory drops it, and the room goes black) is survived: on `webglcontextrestored` the studio the surfaces mirror is made again (`scene.environment`, a render-target texture that the loss empties) and the frame is drawn again (`world.onRestore()` for the table's own redraw).
- The card table's felt is chosen in Settings (`almanac_felt_v1`: `black`, the default; the light `tan`, `ivory`, `dove`, `lilac` (Pastel purple) and `cream`; the dark `chocolate`, `mahogany` and `crimson`; `FELT_CHOICES` in `index.html`, its swatches sampled from the rendered cloth, carried by a backup's prefs) and dresses both the shot's table and the card table (`FELTS`/`dressFelt()` in `intro.mjs`; `setFelt()` on the intro's API and the table's controller, live) - for a skin with a table only: another skin's shot keeps the house's black, which its landing is designed over. On the lighter cloths the gold print takes a dark umber keyline (`printFor()` in `buildCardTable()`) so it reads, the cards' shadows deepen (`shadeCard()`), and the landing's copy is printed on the cloth rather than veiled (`html[data-felt]`, set to the felt the shot is dressed in: dark ink, the gold keylined, a black lacquer button - see app.css); the lab's `?felt=` overrides the choice. A new light cloth must also be added to the `html:is([data-felt=...])` lists in app.css, or the landing's copy stays veiled on it.
- The trim round the felt is chosen the same way (`almanac_trim_v1`: `gold`, the default, `onyx`, `silver`, `crimson`, `burgundy`; `TRIM_CHOICES` in `index.html`, carried by a backup's prefs): the filigree band inlaid in the felt, the fine lines either side of it and the line let into the card table's walnut edge (`TRIMS`/`dressTrim()` in `intro.mjs`; `setTrim()` on the intro's API and the table's controller, live; the lab's `?trim=`). ## Cloud Sync

- **On by default, opt-out.** `isSyncEnabled()` reads the enabled key against the literal string `'false'` - an unset key (fresh install) is enabled. `initSync()` runs at boot regardless of the landing screen and signs the device into an anonymous Supabase account automatically (`ensureSyncSignedIn()`), no button click required; `dismissLanding()` also kicks a sync attempt for immediacy. The Settings toggle (`toggleCloudSync()`) is the opt-out, not the opt-in - don't revert this to "disabled by default" without discussion, that was a deliberate later change from the original opt-in design.
- Client code lives in the "Cloud sync" block in the inline script in [index.html](index.html) (search for `SUPABASE_URL`); server schema is the `collection_events` table in the Supabase project (`ewfvyrhlsanzkmozrmhs`) managed via migrations applied through the Supabase MCP tools, not a checked-in `.sql` file - use `list_migrations`/`execute_sql` against that project to inspect it. The `id` column is `text`, not `uuid` - it holds the app's own `uid()`-style ids (e.g. `id_yar7dm8yd`), not real UUIDs; this was a real bug once (every push 400'd) before the column type was fixed to match.
- It's an outbox-and-replay design over `collectionHistory` only (the ledger behind streaks/stats - not `trackedGames`, not settings): local mutations enqueue an op via `enqueueHistorySync(entry, deleted)` (a no-op while sync is disabled), `flushSyncOutbox()` pushes it (upsert by id), `pullAndReplay()` fetches rows changed since the last cursor and applies them locally by id, tombstoning (`deleted: true`) rather than hard-deleting so other devices learn about removals instead of resurrecting them. `kickSync()` is the shared "try now" entry point (seed-if-needed + flush + pull) used by every automatic trigger; `initSync()` sets up the recurring interval/listener exactly once and must not be called more than once per page load.
- Every `collectionHistory` entry needs a stable `id` (assigned by `ensureHistoryEntryIds()` on load, and inline wherever a new entry is created) for this to work - preserve that if you touch collection-history code, even when sync itself isn't what you're changing.
- The anon/publishable key in `index.html` is meant to be public (protected by RLS, not secrecy) - don't treat it as a secret to scrub, but also don't add anything there that would need to be one.
- Browser roles start with nothing: the `least_privilege` migration revoked the default table grants from `anon`/`authenticated` and changed the default privileges, so a new table or RPC is unreachable until its migration says `GRANT` explicitly. Views are `security_invoker`; a public view needs a published-row policy and column grants on its tables, not `SECURITY DEFINER`.
- The catalogue's own RPCs (`get_catalog`, `publish_catalog`, the owner's reports) live in the `catalog_service` migration. Merging a [data/catalog.json](data/catalog.json) change to `main` publishes it through the Publish catalogue workflow; a branch alone changes nothing users see.

### Email linking (device-independent recovery)

- Anonymous auth alone has no credential to sign back in with elsewhere - clearing a device's storage loses local access to that device's cloud copy. Email linking closes that gap: `linkEmailToAccount()` attaches an email to the CURRENT (anonymous) account via `client.auth.updateUser({ email })` - same user id, same data, now with a credential. `sendRecoverySignIn()` is the opposite direction - pulling a previously-linked account's data onto a new/wiped device via `client.auth.signInWithOtp({ email, options: { shouldCreateUser: false } })`. `shouldCreateUser: false` is load-bearing: without it, recovering with an email that was never linked to anything would silently create a new blank account instead of failing, which would look like recovery while doing the opposite. Keep that flag.
- Both flows use passwordless email links, not passwords - no password field exists anywhere in this UI, and none should be added without discussion.
- `getEmailRedirectTo()` resolves to `window.location.origin + window.location.pathname` at call time - no hardcoded production URL, since there's no build step to bake one in and the app also runs on GitHub Pages subpaths, custom domains, and localhost. This only works if that exact resolved URL (or a matching wildcard) is in the Supabase project's Auth "Redirect URLs" allow list (dashboard, not available via any MCP tool here) - if email links stop completing after a domain change, check that list first, not the code.
- `getSupabaseClient()` registers a single `onAuthStateChange` listener (fires on the routine anonymous sign-in too, not just an email link completing) that repaints the email section and kicks a sync attempt - don't register a second one elsewhere, and don't call `initSync()` more than once per page load for the same reason `kickSync()`'s interval/listener setup already warns about above.
- `renderSyncEmailUI()` distinguishes a linked account from anonymous via `session.user.is_anonymous` - an anonymous session still has RLS access (`authenticated` role either way), so this is a display/UX signal, not a security boundary; don't repurpose it as one.

### First-collect email gate

- `markCollected()`, `collect()`, `collectCurrentDailyRun()`, and `openDrop()` (only when it would actually log a collection) each open with `interceptForEmailGate(retryFn)` - a synchronous check against `cachedHasLinkedEmail`/`EMAIL_GATE_PASSED_KEY`, not an async session lookup, since these are synchronous `onclick` handlers. If it returns `true` the caller must return immediately without doing any of its own work; `retryFn` is what re-runs the original action once the gate clears, so add the check to any NEW function that logs a collection the same way, and keep it a closure over the same args the original call had.
- `collectCurrentDailyRun()` is gated at its own level even though it calls `collect()`, which is also gated - `collect()` bailing out on its own wouldn't stop the daily-run wrapper from still advancing `dailyRunIndex`/stats as if the collection had happened. Any future wrapper around a gated function needs the same double-gating, not just the inner call.
- The gate only requires *submitting* an email (`linkEmailCore()` resolving, i.e. the confirmation email queued), not waiting for the confirmation click - that's a deliberate friction tradeoff (chosen explicitly over a harder "block until confirmed" gate and a softer "just nag, never block" one), not an oversight. Don't tighten it to wait for confirmation, or loosen it to a dismissible reminder, without discussion.
- Browsing, adding/removing platforms, and every non-collecting action stay completely ungated - only actions that call `logCollection()` (directly or via the functions above) are.
- Canceling the gate (`cancelEmailGate()`) must never let the pending action through - it only clears `pendingGatedAction` and closes the modal. There is no bypass path; verify this stays true if this code is touched.

## Change Hygiene

- Read the owning abstraction and a nearby call site before editing.
- Keep `index.html` syntax-valid; an inline-script error breaks the shipped app.
- Run reference checks after renaming or adding local files.
- Bump `CACHE_NAME` in [sw.js](sw.js) and `APP_BUILD` in [index.html](index.html) together whenever a shipped file changes (`npm run check:refs` fails if they differ). A new build downloads every file except the rare tiers' extras (`assets/intro3d/rare/`) while the landing shows its "Updating" bar, and the intro waits for that download and a refresh (`appWhenCached()`). A new asset must be added to `PRECACHE_URLS`; `check:refs` fails if one is missing.
- After a catalogue edit, run `npm run build:seo` (the pages and history are generated from the file); merging to `main` publishes the catalogue.
- Keep editor-local `.vscode/` settings and personal Git/Copilot overrides out of the repository.
- Avoid reformatting unrelated sections.
